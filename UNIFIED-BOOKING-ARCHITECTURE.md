# Unified Booking & Payment Architecture — GAIA Tours & Travel

> **Scope:** database + service-layer architecture preparation only.
> **No CyberSource integration. No real payment processing. No external API calls.**
> This document describes the scalable, unified booking → payment → invoice → timeline
> workflow that supports Tours, Hotel Rooms, Events and Transfers, and is ready to
> connect to CyberSource later **without a database redesign**.

---

## 1. Objective

A single booking architecture that supports all service types through one reusable
workflow, with a gateway-independent payment readiness layer. A future CyberSource
driver can be plugged in via `GatewayManager` without changing any booking tables or
business logic.

---

## 2. Unified Booking References

Every booking type gets a unique, auto-generated `booking_reference`:

| Service   | Booking table      | Reference format     | Prefix |
|-----------|--------------------|----------------------|--------|
| Tour      | `weroad_bookings`  | `GAIA-TO-XXXXXX`     | `GAIA-TO-` |
| Hotel     | `hotel_bookings`   | `GAIA-HO-XXXXXX`     | `GAIA-HO-` |
| Room      | `room_bookings`    | `GAIA-RO-XXXXXX`     | `GAIA-RO-` |
| Event     | `event_bookings`   | `GAIA-EV-XXXXXX`     | `GAIA-EV-` |
| Transfer  | `bookings`         | `GAIA-TR-XXXXXX`     | `GAIA-TR-` |
| Taxi      | `taxi_bookings`    | `GAIA-TR-XXXXXX`     | `GAIA-TR-` |

- Generated by `services/BookingReferenceService.php` (collision-safe retry loop + unique DB index).
- Each booking table has a `booking_reference` column with a **unique index**.
- Existing rows are backfilled by migration `schema-migration-11.sql`.

## 3. Standardised Booking Status

All booking tables share the same canonical status set:

```
pending → awaiting_payment → paid → confirmed → completed
         (cancelled / refunded at any relevant stage)
```

**Canonical statuses:** `pending`, `awaiting_payment`, `paid`, `confirmed`, `completed`, `cancelled`, `refunded`

**Helper functions** (`auth/helpers.php`):
- `booking_status_list()` — canonical list
- `normalize_booking_status()` — maps legacy values, falls back to `pending`
- `booking_status_label()` — localized label
- `booking_status_badge_class()` — CSS badge class

`services/BookingService.php` enforces valid lifecycle transitions via a `TRANSITIONS` map.

## 4. Payments Table

`payments` — unified across all booking types, gateway-ready.

| Field | Purpose |
|-------|---------|
| `id` | PK |
| `user_id` | owning user (ownership guard) |
| `booking_type` | transfer / tour / hotel / room / event / taxi |
| `booking_id` | booking record id |
| `booking_reference` | GAIA-* reference |
| `amount` | payment amount |
| `currency` | ISO code |
| `payment_method` | card / manual / etc. |
| `gateway` | gateway name (empty until CyberSource) |
| `transaction_reference` | gateway transaction id (future) |
| `authorization_code` | CyberSource authorization code (future placeholder) |
| `payment_token` | payment token (future placeholder) |
| `gateway_response` | gateway response stored as JSON, never exposed publicly |
| `status` | pending / authorized / paid / failed / cancelled / refunded |
| `created_at` / `updated_at` | timestamps |

`payment_transactions` — one payment can have many gateway transaction records
(authorize / capture / sale / refund / void / webhook), storing request/response/webhook
payloads as JSON for future reconciliation.

---

## 5. Invoices Table

`invoices` — generic and reusable for every booking type.

| Field | Purpose |
|-------|---------|
| `id` | PK |
| `user_id` | owning user |
| `booking_type` / `booking_id` / `booking_reference` | booking link |
| `invoice_number` | auto-generated `INV-YYYY-NNNNNN` (e.g. `INV-2026-000001`) |
| `subtotal` / `tax_amount` / `discount_amount` / `total_amount` | price composition |
| `currency` | ISO code |
| `status` | draft / issued / paid / void / cancelled |
| `issued_at` / `created_at` / `updated_at` | timestamps |

Invoice numbers are generated automatically by `services/InvoiceService.php::nextInvoiceNumber()`.
**No PDF generation yet** — this is database + architecture preparation.

## 6. Booking Summary System

`services/BookingSummaryService.php` exposes a consistent summary for every booking type:

- `booking_reference`
- `service_name`
- `customer`
- `amount`
- `status`
- `created_date`

This powers the customer dashboard, admin/hotel dashboards, payments and invoices.
`components/booking-summary.php` is the reusable presentation component rendering:
booking info, customer info, payment status, invoice status, and timeline history.

---

## 7. Payment Service (Payment Readiness Layer)

`services/PaymentService.php` — gateway-independent.

Responsibilities:
- `createPayment()` — create a payment record
- `updatePaymentStatus()` — update payment status + sync booking status
- `createInvoice()` — create an invoice from a payment
- `linkBookingToPayment()` — link booking to payment
- `logGatewayResponse()` — store gateway response JSON
- `getUserPayments()` / `getBookingPayments()` / `getBookingPayment()` — ownership-scoped reads
- `ownsPayment()` — IDOR guard

`services/GatewayManager.php` is the **CyberSource-ready** abstraction layer:
- `GatewayContract` interface (authorize / capture / sale / refund / void / handleWebhook)
- `register()` / `resolve()` for future drivers
- `recordTransaction()` — stores gateway transaction + payloads locally (no API call)

## 10. Future CyberSource Requirements (placeholders only)

All of the following are **already present in the schema** as placeholders — **no API calls**:

| Placeholder | Column / structure |
|-------------|--------------------|
| Gateway Name | `payments.gateway` |
| Transaction ID | `payments.transaction_reference` + `payment_transactions.transaction_reference` |
| Authorization Code | `payments.authorization_code` |
| Payment Token | `payments.payment_token` |
| Gateway Response JSON | `payments.gateway_response` + `payment_transactions.{request,response,webhook}_payload` |

To integrate CyberSource later, implement a class implementing `GatewayContract` and
register it: `GatewayManager::register('cybersource', CyberSourceDriver::class);`

## 12. Architecture Diagram — Booking → Payment → Invoice Flow

```
                        ┌────────────────────────────────────────────┐
                        │        BOOKING CREATION (per type)          │
                        │  process_booking.php / weroad/process...    │
                        └────────────────────────────────────────────┘
                                             │
           generates booking_reference (GAIA-*)  &  status = awaiting_payment
                                             ▼
                              ┌──────────────────────────────┐
                              │   BOOKING TABLE  (per type)   │
                              │  bookings / weroad_bookings   │

                              │  event_bookings / taxi_bookings│
                              └──────────────────────────────┘
                                             │
                         BookingTimelineService::logBookingCreated()

                              ┌──────────────────────────────┐
                              │     booking_logs  (audit)     │
                              └──────────────────────────────┘
                                             │
                          PaymentService::createPayment()
                                             ▼
                              ┌──────────────────────────────┐
                              │         payments             │
                              │  (status = pending)          │
                              └──────────────────────────────┘
                                             │
                                 GatewayManager (future driver)
                                             ▼
                              ┌──────────────────────────────┐
                              │    payment_transactions      │

                                             │

                              ┌──────────────────────────────┐
                              │         invoices             │

                                             │

                    Customer / Admin / Hotel Manager dashboards
                    (My Bookings / My Payments / My Invoices)
```

## 14. Security

- Booking ownership validated via `user_id` scoping (`BookingRepository`, `BookingSummaryService`).
- Payment ownership validated via `PaymentService::ownsPayment()` / `getUserPayments()`.
- Invoice ownership validated via `InvoiceService::getForUser()` / `get()`.
- Timeline ownership validated via `BookingTimelineService::getTimeline()`.
- Gateway data is **never** returned to public pages — only safe metadata (status/labels).
- Payment responses stored securely as JSON with PDO prepared statements.
